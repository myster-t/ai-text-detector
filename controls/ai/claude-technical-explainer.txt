A hash table stores key-value pairs so that looking up a value by its key takes, on average, constant time regardless of how many pairs the table holds. It achieves this with a hash function, which converts a key into an integer, and an array, where that integer (reduced modulo the array length) selects a slot.

The central difficulty is collisions. Two different keys can hash to the same slot, and with enough keys they inevitably will. Hash tables handle this in one of two broad ways. Separate chaining keeps a small linked list or dynamic array at each slot and appends colliding entries to it. Open addressing stores every entry directly in the main array and, on a collision, probes other slots according to a fixed rule until it finds an empty one. Linear probing checks the next slot, then the one after, and so on; quadratic probing and double hashing spread the probes out to reduce clustering.

Performance depends on the load factor, the ratio of stored entries to array slots. As the load factor climbs, collisions become frequent and lookups slow down. Most implementations resize the array, typically doubling it, once the load factor crosses a threshold such as 0.7, and rehash every existing entry into the larger array. Resizing is expensive, but it happens rarely enough that the amortized cost per insertion stays constant.

The quality of the hash function matters as much as the collision strategy. A good function distributes keys uniformly across slots and is fast to compute. A poor one, or one that an adversary can predict, can force every key into the same slot and degrade the table into a linked list with linear lookup time, which is why some languages randomize their string hashing at process start.
